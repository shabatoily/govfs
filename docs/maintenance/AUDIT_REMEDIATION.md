## 1. 작업 원칙

- 보안 경계와 데이터 손실 방지를 먼저 수정한다. 기존 드라이버·미들웨어·표준
  라이브러리를 재사용하고, 새 의존성은 필요성이 확인된 경우에만 추가한다.
- 수정 전에 실제 실패를 보여 주는 작은 회귀 테스트를 추가한다. 테스트 기대값을
  현재 결함에 맞추지 않는다.
- 기존 사용자 데이터는 자동 삭제하거나 덮어쓰지 않는다. 경로 정규화 충돌,
  인덱스 불일치, 암호화 키 불일치는 별도 복구가 필요한 상태로 보고한다.
- 파일과 인덱스, 암호화 키와 registry처럼 여러 파일이 함께 바뀌는 작업은
  정상 경로뿐 아니라 실패·강제 종료 이후 복구 방법을 확정하고 구현한다.
- 감사에서 확인하지 않은 조건은 재현 후 판단한다. 특히 운영체제별 rename,
  symlink, 암호화 키 교체 동작을 추정만으로 완료 처리하지 않는다.
- 13번은 선택적 정리 작업이다. 1–12번의 수정과 별도 변경으로 진행한다.

## 3. 항목별 수정 범위와 완료 조건

### 1. LocalStorage 경로 격리와 정규화

**문제와 근거**

[LocalStorage](../../pkg/drivers/localstorage/localstorage.go)의 `toLocalPath`는
입력 경로를 실제 저장소 경로에 결합하지만 저장소 경계를 강제하지 않는다.
`Create`는 정규화 전 문자열로 중복을 확인한다. `validateRestoredFiles`는
디렉터리를 건너뛰므로 복원 인덱스의 경로 이탈도 허용한다.

감사 시 `/../outside.txt` 생성으로 저장소 밖에 파일이 쓰였고, `/./a.txt`
생성으로 기존 `/a.txt`가 덮어써졌다. `isDir=true`, `/../victim/`인 복원
메타데이터는 검증을 통과했으며, 해당 ID 삭제로 형제 디렉터리가 삭제됐다.

**수정 작업**

- 생성·조회·쓰기·삭제·이동·복사에 일관된 경로 정규화와 검증을 적용한다.
- 정규화된 경로로 중복과 교체 조건을 확인한다. 내부 인덱스 파일명과 작업용
  경로를 사용자가 파일 경로로 점유하지 못하게 한다.
- 파일·디렉터리 모두 복원 인덱스의 경로, ID 중복, 경로 중복, 항목 유형을
  검증한다. 기존 인덱스를 읽을 때도 안전하지 않은 항목을 묵인하지 않는다.
- `os.Root` 등 표준 라이브러리로 실제 파일 접근을 저장소 안에 제한한다.
  문자열 검사만으로 symlink를 통한 경계 이탈을 허용하지 않는다.
- HTTP 서비스·드라이버 직접 호출·CLI·MCP의 입력 경로를 함께 확인한다.
  [전송 경로 규칙](../../transfer.go)은 가능한 범위에서 재사용한다.

**완료 조건**

- `..`, 경로 별칭, 저장소 밖을 가리키는 symlink로 외부 파일을 읽거나
  생성·교체·삭제할 수 없다. 실패 시 외부 파일은 변경되지 않는다.
- 동일한 실제 경로를 가리키는 입력은 중복 생성으로 원본을 덮어쓰지 않는다.
- 악성 복원 인덱스의 디렉터리 경로도 거부하며 기존 드라이브를 보존한다.
- 서로 다른 사용자 드라이브를 대상으로 HTTP 격리 회귀 테스트가 통과한다.

### 2. Badger 암호화 키 회전

**문제와 근거**

[BadgerVFS.Rotate](../../pkg/drivers/badger/badger.go)는 registry를 새 키로
기록하지만 [키 파일 처리](../../pkg/drivers/badger/utils.go)와 동기화하지 않는다.
감사 시 회전 성공 후 DB를 닫고 다시 열면 `Encryption key mismatch`가 발생했다.

**수정 작업**

- 열린 DB의 쓰기·읽기·백업·유휴 종료와 키 회전 사이의 동시 실행을 제어한다.
  DB가 사용하는 registry와 디스크 registry가 서로 달라지지 않게 한다.
- 지원되는 AES 키 길이를 검증하고 registry·키 파일을 함께 갱신한다.
- 기존 키·registry의 백업, 오류 시 복구, 강제 종료 후 재개 방법을 마련한다.
  새 키로 재개방을 확인하기 전에는 성공을 반환하지 않는다.
- [Badger 핸들러](../../internal/server/handlers/badger.go),
  [DriveManager](../../internal/server/services/drives.go), CLI `rotate`의 동작과
  사용자 안내를 최종 회전 방식에 맞춘다.

**완료 조건**

- 파일을 생성하고 회전한 뒤 DB·서버를 재시작해 원래 파일을 읽고 새 파일을 쓸 수 있다.
- 잘못된 키, 키 파일 쓰기 실패, registry 교체 실패에 기존 데이터가 보존된다.
- 회전 도중의 요청·종료와 교체 단계 사이의 강제 종료를 검증한다.
- 복구 실패 시 기존 백업을 보존하고 복구 위치를 출력한다.

### 3. LocalStorage 인덱스 영속화

**문제와 근거**

[LocalStorage](../../pkg/drivers/localstorage/localstorage.go)는 변경 내역을 메모리
map에 반영하고 `Close`에서만 `saveIndex`를 호출한다. 감사 시 종료 전 새로 연
인스턴스는 생성된 파일의 ID를 조회하지 못했다.

**수정 작업**

- Create, Write, WriteComments, Delete, Mkdir, Move, Copy의 성공 결과를 영속화한다.
- 파일 변경·인덱스 갱신 순서와 복구 방법을 정한다. 인덱스 저장만 추가하고
  파일은 이미 바뀐 실패 상태를 성공·원상 복구로 잘못 처리하지 않는다.
- 여러 단계가 필요한 작업은 중단 후 불일치를 감지하고 복구할 수 있게 한다.
- 기존 인덱스가 불일치할 때 파일을 조용히 삭제하거나 빈 인덱스로 교체하지 않는다.

**완료 조건**

- 변경 완료 이후 정상 종료 없이 프로세스를 중단하고 재시작해도 완료된 변경을 조회할 수 있다.
- 인덱스 저장 실패와 파일 교체 사이의 중단을 검증하고, 원본·백업을 보존한다.
- 생성·수정·삭제·디렉터리 이동·복사·코멘트가 재시작 후 일관되게 유지된다.

### 4. LocalStorage 쓰기 실패 시 원본 보존

**문제와 근거**

[LocalStorage.Write](../../pkg/drivers/localstorage/localstorage.go)는 `os.Create`로
기존 파일을 먼저 비우고 데이터를 복사한다. 감사 시 reader 오류가 반환됐지만
기존 내용은 `partial`로 바뀌었다. Create와 Write는 파일 닫기 오류도 무시한다.

**수정 작업**

- 같은 파일 시스템의 임시 파일에 복사하고 copy·close 오류를 확인한다.
- 모든 검증이 끝난 파일만 최종 경로로 교체한다. 실패한 임시 파일을 정리한다.
- 최종 파일 크기·수정 시각·ID를 3번의 인덱스 저장 절차와 일치시킨다.
- 생성 중 실패로 물리 파일만 남는 경우와 동시 읽기의 동작도 확인한다.

**완료 조건**

- reader 오류·출력 오류·교체 실패 시 이전 내용과 메타데이터가 유지된다.
- 성공 시 전체 새 내용이 읽히며 임시 파일이 남지 않는다.
- 이전 파일을 읽던 요청과 새 요청의 결과가 각각 일관된다.

### 5. Badger 생성 실패 청크 정리

**문제와 근거**

[BadgerVFS.Create](../../pkg/drivers/badger/badger.go)는 청크 기록 이후 메타데이터
트랜잭션이 실패하면 새 청크를 정리하지 않는다. 중복 생성 실패를 재현했을 때
blob 개수는 1에서 2로 증가했다.

**수정 작업**

- 중복 경로·부모 누락·트랜잭션 실패 시 이번 생성의 internal ID에 해당하는
  청크를 정리한다. 기존 Write의 실패 처리 방식을 재사용한다.
- 정리 자체가 실패하면 오류를 숨기지 않는다. 기존 파일의 청크를 삭제하지 않는다.

**완료 조건**

- 중복 생성·부모 누락을 반복해도 blob 수와 기존 파일 내용이 변하지 않는다.
- 생성 중 오류와 정리 오류를 검증하며, 성공한 업로드의 청크는 유지된다.

### 6. 비밀번호 변경 시 토큰 무효화

**문제와 근거**

[사용자 인증 미들웨어](../../internal/server/middlewares/auth.go)는 JWT subject와
계정 상태를 확인하지만 비밀번호 변경 여부를 확인하지 않는다.
[사용자 갱신](../../internal/server/services/users.go)은 password hash만 변경한다.

**수정 작업**

- 사용자 레코드와 로그인 토큰에 세션 버전을 추가한다.
- 본인 비밀번호 변경과 관리자 비밀번호 초기화에서 버전을 증가시킨다.
- 인증 시 서명·만료·계정 상태와 함께 세션 버전을 확인한다.
- 기존 레코드·버전 없는 토큰의 전환 정책을 명시한다. 기존 토큰을 허용해
  초기화 효과가 없어지는 우회는 만들지 않는다.
- 웹 UI·CLI·MCP에서 기존 세션 무효화 후 재로그인을 안내한다.

**완료 조건**

- 이전 토큰으로 비밀번호 변경·관리자 초기화 이후 요청하면 401을 받는다.
- 새 비밀번호 로그인은 성공하고, 다른 사용자의 토큰은 유지된다.
- 기존 DB 업그레이드와 토큰 전환 시 필요한 재로그인이 문서화된다.

### 7. pprof 관리자 인증

**문제와 근거**

[미들웨어 등록](../../internal/server/middlewares/register.go)의 `/debug/pprof/*`는
활성화됐을 때 다른 진단 경로와 달리 인증·관리자 검사를 거치지 않는다.

**수정 작업**

- 기존 JWTAuthMiddleware, UserMiddleware, AdminOnly를 실제 pprof 경로에 적용한다.
- pprof 미들웨어가 등록하는 하위 경로까지 보호되는지 확인한다.

**완료 조건**

- 기능 활성화 상태에서 비인증 사용자는 401, 일반 사용자는 403을 받는다.
- 관리자는 진단을 사용할 수 있고, 비활성화 상태에서는 진단 기능이 노출되지 않는다.

### 8. 미디어 캐시 정책

**문제와 근거**

[VfsHandler.Read](../../internal/server/handlers/vfs.go)는 이미지·영상·음성·PDF에
1년 max-age를 설정한다. 같은 ID의 내용 변경에도
[웹 UI 읽기](../../webui/src/lib/vfs.ts)는 같은 URL을 사용한다.

**수정 작업**

- 인증된 변경 가능 파일에는 `private, no-cache`로 재검증을 요구한다.
- 로그아웃 이후 캐시 접근까지 막아야 하는 응답은 `no-store`를 적용한다.
- ETag가 실제 스트리밍 파일의 변경을 구분하는지 확인한다. 신뢰할 수 없는
  validator로 304를 반환하지 않는다.

**완료 조건**

- 같은 ID의 내용 수정 후 재조회에서 새 내용을 받는다.
- 삭제·계정 전환 이후 캐시가 서버의 접근 검사나 실패 응답을 우회하지 않는다.
- 일반 다운로드와 Range Request의 기존 동작이 유지된다.

### 9. LocalStorage 부모 디렉터리 일관성

**문제와 근거**

[LocalStorage.Create](../../pkg/drivers/localstorage/localstorage.go)는 물리 부모
디렉터리를 만들지만 인덱스에 부모를 등록하지 않는다. 감사 시
`/hidden/child.txt` 생성은 성공했지만 root tree에는 나타나지 않았다.

**수정 작업**

- 최소 변경으로 Badger와 동일하게 등록된 부모 디렉터리를 요구한다.
- Mkdir·Move·Copy의 목적지 부모 검증에도 같은 규칙을 적용한다.
- [CLI 재귀 업로드·mkdir -p](../../internal/cli/vfs/vfs.go)가 부모 생성의
  202 접수만 받고 자식 작업을 시작하지 않도록 완료 순서를 검증한다.

**완료 조건**

- 부모 누락 요청은 물리 파일·디렉터리를 남기지 않고 실패한다.
- 등록된 부모 아래의 파일은 List·Tree·Search·사용량 집계에 나타난다.
- 부모 생성이 지연되는 조건에서도 재귀 업로드·mkdir -p의 결과가 일관된다.

### 10. MCP 완료 이벤트 오인 방지

**문제와 근거**

[MCP 완료 대기](../../internal/mcp/server.go)는 이벤트의 action만 비교한다.
첫 create가 시간 초과된 뒤 늦게 도착하면 다음 create가 그 결과를 받을 수 있다.

**수정 작업**

- 첫 구현은 취소·시간 초과 이후 기존 완료 스트림을 재사용하지 않도록 한다.
  서버 작업이 취소됐다고 가정하거나 같은 요청을 자동 재시도하지 않는다.
- 이후 작업은 MCP 재연결이 필요함을 명확히 알린다.
- 같은 스트림의 계속 사용이 필요할 때만 HTTP 요청과 SSE에 request ID를
  연결한다. action이나 경로만으로 일반적인 요청 상관관계를 보장하지 않는다.

**완료 조건**

- 첫 요청 취소 후 늦은 이벤트를 주입해도 두 번째 요청의 성공으로 처리하지 않는다.
- 기존 정상 완료·실패 이벤트는 처리하고, 잠금·구독 리소스를 정리한다.
- 시간 초과는 결과 불확실 상태로 안내하며 서버 작업 완료 여부를 단정하지 않는다.

### 11. Docker 버전·빌드 시각 주입

**문제와 근거**

[Dockerfile](../../Dockerfile)은 `main.version`, `main.buildTime`에 linker 값을
주입하지만 실제 변수는 [pkg/version](../../pkg/version/version.go)에 있다.

**수정 작업**

- [Makefile](../../Makefile)의 package-qualified linker 대상을 사용한다.
- [.github/workflows/release.yml](../../.github/workflows/release.yml)의 Docker
  build arguments가 VERSION과 BUILD_TIME을 모두 전달하도록 맞춘다.

**완료 조건**

- 지정한 VERSION으로 이미지 빌드 후 `govfs version`이 해당 버전을 출력한다.
- 빌드 시각이 주입되며 `unknown` 기본값으로 남지 않음을 확인한다.
- 기존 이미지의 기본 실행·설정 파일 경로·healthcheck가 유지된다.

### 12. CLI 다운로드·백업 스트리밍

**문제와 근거**

[VFSClient.Read·Backup](../../internal/client/vfs.go)는 전체 응답을 메모리에 받은
후 복제한다. [CLI 백업](../../internal/cli/vfs/vfs.go)의 임시 파일 저장은
이미 전체 데이터를 받은 뒤 시작된다.

**수정 작업**

- 스트리밍 응답 body를 반환하고, 소비자가 close할 책임을 명확히 한다.
- 단일·재귀 다운로드와 백업에서 응답을 임시 파일로 복사한다.
- 상태 코드·취소·연결 중단·파일 쓰기·close 오류를 확인하고 성공한 결과만 교체한다.
- 실제 응답 크기와 메타데이터가 다를 때 완료된 다운로드로 처리하지 않는다.

**완료 조건**

- 크기가 증가해도 파일 크기에 비례하는 전체 응답 버퍼·복제가 발생하지 않는다.
- 충분한 임시 디스크에서 대용량 다운로드·백업의 내용 hash가 일치한다.
- 연결 중단·취소·디스크 오류 시 기존 출력 파일은 보존되고 임시 파일과 body는 정리된다.

### 13. 선택적 cloud 코드·의존성 정리

**문제와 근거**

삭제 전 `internal/cloud/cloud.go`와
`internal/cloud/googledrive/drive.go`는 애플리케이션
호출 경로에 연결되지 않는다. 현재 합계 445줄이며 oauth2·Google API 직접

**수정 작업**

**완료 조건**

- cloud 참조가 끊어진 채 남지 않으며 서버·CLI·MCP·웹 UI가 기존 기능을 제공한다.
- `go.mod`·`go.sum`에 불필요한 의존성이 정리되고 audit·테스트·빌드가 통과한다.

### 데이터·세션 전환과 복구

- 이전 릴리즈에서 발급한 세션 버전 없는 토큰은 거부한다. 업그레이드 후
  웹 UI·CLI를 다시 로그인하고 MCP도 새 세션으로 재연결한다.
- LocalStorage의 `.vfs*` 이름은 예약한다. 기존 인덱스의 비정규 경로,
  중복 ID·경로, 부모 누락, 파일 유형·크기 불일치는 시작 시 오류로 보고한다.
  자동으로 데이터를 지우거나 인덱스를 재구성하지 않는다. 기존 데이터와
  인덱스를 먼저 백업하고 오류 항목을 복구한 뒤 다시 시작한다.
- `.vfs-transaction`은 재개방 시 미완료 이동을 되돌리는 복구 기록이다.
  복구 실패 시 작업을 중단하고 원본을 보존하므로 이 디렉터리를 임의 삭제하지 않는다.
- Badger `.key-rotation`도 재개방 시 자동 복구에 사용한다. 진행 중인 DB
  작업이 끝난 뒤 회전하며, 유휴 reader 자체를 잠금으로 붙잡지 않는다.
  실제 Read 호출과 회전을 직렬화해 스트림이 새 DB에서 계속 읽게 한다.
- CLI 스트리밍 Read·Backup의 반환값은 `io.ReadCloser`다. 호출자는 사용 후
  닫아야 한다. 정상 다운로드·백업 파일만 최종 위치로 교체한다.
- MCP의 불확실한 변경은 서버에서 계속 실행될 수 있다. 재연결 후 상태를
  확인하고, 중복 생성·삭제가 될 수 있는 자동 재시도는 하지 않는다.
