# 사용자 및 독립 드라이브 설계

## 목적

govfs에 관리자와 일반 사용자 계정을 추가하고, 각 사용자가 독립된 가상 드라이브를 사용하게 한다. 사용자별로 별도의 BadgerDB 디렉터리, 암호화 키 및 `BadgerVFS` 객체를 할당하여 애플리케이션 오류로 다른 사용자의 파일이 함께 조회되거나 조작되는 위험을 줄인다.

기존 `vfs.VFS` 인터페이스, Badger 키 구조와 파일 저장 방식은 변경하지 않는다.

## 범위

초기 구현은 다음 기능만 포함한다.

- 사용자 로그인과 현재 사용자 조회
- CLI의 명시적인 로그인과 로컬 세션 저장
- 관리자와 일반 사용자 역할
- 관리자의 사용자 생성, 목록 조회, 수정 및 비활성화
- 인증된 사용자별 독립 Badger VFS 선택
- 사용자별 SSE 구독 및 파일 변경 이벤트 격리
- 서버 상태와 사용자 드라이브의 제한된 운영 지표 조회
- 로그인 및 데이터 변경 이벤트의 최근 히스토리 조회
- 기존 단일 사용자 데이터의 초기 관리자 드라이브 이전

다음 기능은 실제 요구가 생길 때 추가한다.

- 범용 권한 정책 또는 역할 추가
- 사용자별 프로세스, OS 계정 또는 컨테이너 격리
- 저장 용량 쿼터
- 장시간 사용하지 않은 드라이브 자동 종료
- 사용자 간 파일 공유와 관리자의 사용자 파일 접근
- 삭제된 사용자 데이터의 자동 제거
- 사용자별 외부 클라우드 계정 연동

## 권한 모델

역할은 `admin`과 `user`만 사용한다. 별도의 RBAC 프레임워크는 도입하지 않고 관리 라우트에서 역할을 직접 검사한다.

| 기능 | 관리자 | 일반 사용자 |
| --- | --- | --- |
| 자신의 파일 조회 및 조작 | 가능 | 가능 |
| 자신의 백업, 복원 및 암호화 키 회전 | 가능 | 가능 |
| 사용자 생성, 목록 조회, 수정 및 비활성화 | 가능 | 불가 |
| 서버 및 DB 운영 상태 조회 | 가능 | 불가 |
| 다른 사용자의 파일, 경로, 메타데이터 및 Badger 키 조회 | 불가 | 불가 |
| 다른 사용자의 백업, 복원 및 암호화 키 회전 | 불가 | 불가 |

관리자 역할은 관리 API 사용 권한만 추가한다. 파일 API는 역할과 관계없이 JWT의 사용자 ID에 해당하는 드라이브만 사용한다.

## 데이터 배치

시스템 데이터와 사용자 파일 데이터를 서로 다른 BadgerDB에 저장한다.

```text
~/.govfs/
├── system/
│   └── users/                 # 사용자 계정 DB
└── drives/
    ├── {user-uuid}/           # 사용자별 BadgerVFS와 .secret
    └── {user-uuid}/
```

디렉터리 이름에는 변경 가능한 사용자 이름 대신 UUID를 사용한다. 사용자 입력을 파일 시스템 경로 생성에 사용하지 않는다. 각 드라이브의 `.secret`은 현재 Badger 드라이버의 키 생성 및 로딩 방식을 그대로 사용한다.

## 사용자 모델

사용자 DB에는 계정 관리에 필요한 최소 정보만 저장한다.

```go
type Role string

const (
    RoleAdmin Role = "admin"
    RoleUser  Role = "user"
)

type User struct {
    ID           uuid.UUID
    Username     string
    PasswordHash []byte
    Role         Role
    Disabled     bool
    CreatedAt    time.Time
    UpdatedAt    time.Time
}
```

- 사용자 이름은 정규화한 값으로 유일해야 한다.
- 비밀번호는 현재 의존 중인 bcrypt로 해시하며 평문을 저장하거나 로그에 남기지 않는다.
- 역할은 두 상수 외의 값을 거부한다.
- 사용자 삭제는 초기 구현에서 `Disabled` 변경으로 처리한다.
- 비활성화된 사용자의 드라이브 디렉터리는 자동으로 삭제하지 않는다.

사용자 DB에도 BadgerDB를 사용하여 새 저장소 의존성을 추가하지 않는다. 사용자 레코드는 VFS 키 구조와 섞지 않고 시스템 DB 전용 키 공간에 저장한다.

## 인증

기존 설정 파일의 단일 사용자 이름과 비밀번호 비교를 사용자 DB 조회로 교체한다.

로그인 과정은 다음과 같다.

1. 정규화한 사용자 이름으로 활성 사용자를 조회한다.
2. bcrypt로 비밀번호를 검증한다.
3. 사용자 UUID를 JWT `sub`에 넣어 토큰을 발급한다.
4. 이후 인증 요청마다 JWT 검증 후 사용자 DB를 다시 조회한다.
5. 존재하지 않거나 비활성화된 사용자의 요청을 거부한다.

JWT의 역할 정보만 신뢰하지 않고 현재 사용자 레코드의 역할을 사용한다. 이를 통해 비활성화와 권한 변경이 기존 토큰 만료 전에도 적용된다. `/auth/me` 응답에는 사용자 ID, 사용자 이름, 역할 및 토큰 만료 시간을 반환한다.

인증을 비활성화하면 사용자 드라이브를 결정할 수 없으므로 다중 사용자 모드에서는 인증을 항상 활성화한다.

## 초기 관리자

사용자 DB가 비어 있을 때만 `server.auth.admin` 설정으로 최초 관리자 한 명을 생성한다. 이미 사용자가 존재하면 관리자 설정의 자격 증명은 무시한다.

부트스트랩 비밀번호가 없거나 올바른 bcrypt 해시를 만들 수 없으면 서버 시작을 실패시킨다. 운영 중 관리자 추가는 관리 API를 사용한다.

## 드라이브 선택

`DriveManager`가 사용자 UUID별 `BadgerVFS` 객체를 지연 생성하고 재사용한다.

```go
type DriveManager struct {
    root   string
    config badger.Config
    drives map[uuid.UUID]*badger.BadgerVFS
    mu     sync.Mutex
}

func (m *DriveManager) Drive(userID uuid.UUID) (vfs.VFS, error)
func (m *DriveManager) Close() error
```

`Drive()`는 `root/{user-uuid}`를 Badger 경로로 사용한다. 동일 사용자에 대한 동시 최초 요청이 DB를 여러 번 열지 않도록 생성을 잠근다. 서버 종료 시 열린 모든 드라이브를 닫고 오류를 합쳐 반환한다.

초기 구현에서는 열린 드라이브를 서버 종료 때까지 유지한다. 실제 파일 디스크립터 또는 메모리 사용량이 문제가 될 때만 유휴 종료 정책을 추가한다.

## 요청 처리 구조

```text
HTTP 요청
    │
    ▼
JWT 검증
    │ user ID
    ▼
활성 사용자 조회
    │
    ▼
DriveManager.Drive(user ID)
    │
    ▼
요청 범위 VfsService
    │
    ▼
사용자 BadgerVFS
```

현재 서버 시작 시 생성하는 단일 `ctx.VFS`와 고정 `VfsService`를 제거한다. 인증 후 실행되는 VFS 라우트 미들웨어가 사용자 드라이브를 선택하고 요청 범위의 서비스로 전달한다. 핸들러는 URL이나 요청 본문에서 사용자 ID를 받지 않는다.

파일 UUID가 우연히 다른 사용자 드라이브에 존재하더라도 현재 사용자의 BadgerDB에서만 조회하므로 접근할 수 없다.

## SSE 격리

현재 전역 SSE broker를 그대로 사용하면 한 사용자의 파일 변경 이벤트나 클라이언트 정보가 다른 사용자에게 전달될 수 있다. SSE 구독자와 발행 작업을 인증 사용자 ID로 범위화한다.

- 구독 시 현재 사용자 ID를 클라이언트에 기록한다.
- broadcast는 동일 사용자 구독자에게만 전달한다.
- client ID 대상 발행도 요청 사용자 소유인지 확인한다.
- `/sse/clients`는 현재 사용자의 클라이언트만 반환한다.
- 관리자에게도 다른 사용자의 파일 이벤트 또는 클라이언트 상세를 반환하지 않는다.

사용자별 broker 객체를 별도로 만드는 대신 기존 broker에 사용자 범위만 추가하여 생명주기와 종료 처리를 유지한다.

## 관리 API

관리 라우트는 JWT 인증과 `admin` 역할 검사를 모두 적용한다.

```text
GET    /admin/users
POST   /admin/users
PATCH  /admin/users/:id
GET    /admin/status
GET    /admin/events
```

- 사용자 목록에는 계정 정보와 드라이브 사용 여부만 반환한다.
- 사용자 수정은 역할, 비활성화 상태 및 비밀번호 초기화만 지원한다.
- 마지막 활성 관리자를 비활성화하거나 일반 사용자로 변경하는 요청은 거부한다.
- 상태 API는 서버 상태, 시스템 DB 상태와 열린 사용자 DB 수 등 집계 지표만 반환한다.
- 시스템 DB와 사용자별 드라이브의 key 수 및 논리 사용량을 반환한다. 닫힌 사용자 드라이브는 조회 중에만 열고 즉시 닫는다.
- 사용자별 Badger 드라이브 open 여부와 활성 SSE 연결 수를 함께 반환하며, SSE 연결이 하나 이상이면 온라인으로 표시한다.
- 상태 API는 사용자 파일 경로, 파일 메타데이터, Badger 키 및 값을 반환하지 않는다.
- 이벤트 히스토리는 최근 100건의 사용자, 라우트 동작, HTTP 상태와 시각만 반환하며 사용자 ID로 필터링할 수 있다. 요청 본문, 원시 URL 및 파일 ID는 저장하지 않는다.

기존 `/badger/keys`는 내부 파일 키를 노출하므로 관리 API로 승격하지 않는다. 필요하다면 현재 사용자가 자신의 드라이브를 진단하는 개발 기능으로만 별도 보호한다.

## Cloud 모듈

`internal/cloud`와 하위 adapter 구현은 보존하지만 서버 API, 통합 API 클라이언트, CLI 명령 및 애플리케이션 설정에서는 제거한다. 사용자별 외부 저장소 설계가 확정되기 전까지 애플리케이션에서 cloud 모듈을 초기화하거나 노출하지 않는다.

향후 다시 제공할 때는 사용자별 OAuth state 검증, 토큰 저장 경로와 adapter 생명주기를 먼저 설계한다.

## 설정 변경

인증은 사용자 드라이브를 선택하기 위한 필수 기능이므로 `server.auth.enabled`를 제거한다. 기존 `username`과 `password`는 일반 로그인 계정으로 오해하지 않도록 최초 관리자 전용 하위 설정으로 이동한다.

```toml
[server.auth.admin]
username = "${SERVER_AUTH_ADMIN_USERNAME}"
password = "${SERVER_AUTH_ADMIN_PASSWORD}"

[server.auth.jwt]
secret = "${SERVER_AUTH_JWT_SECRET}"
exp = "24h"

[vfs.driver.badger]
path = "~/.govfs/drives"
```

`AuthConfig`에는 JWT 설정과 최초 관리자 설정만 둔다.

```go
type AuthConfig struct {
    Admin AdminConfig `json:"admin"`
    JWT   JWTConfig   `json:"jwt"`
}

type AdminConfig struct {
    Username string `json:"username"`
    Password string `json:"-"`
}
```

서버는 인증 없이 실행되는 호환 모드를 제공하지 않는다. 기존 `SERVER_AUTH_USERNAME`, `SERVER_AUTH_PASSWORD` 및 `server.auth.enabled`는 제거하며 자동 변환이나 deprecated alias는 유지하지 않는다.

VFS의 기존 Badger 설정은 사용자 드라이브의 공통 템플릿으로 재사용한다. `path`는 단일 DB 경로가 아니라 드라이브 루트가 된다.

캐시 크기, GC 주기 및 암호화 키 회전 주기는 각 사용자 Badger 객체에 동일하게 적용한다. 사용자별 설정은 초기 범위에 포함하지 않는다.

## CLI 로그인

기존 `govfs config` 명령은 `govfs login`으로 교체한다. `login`은 입력값을 저장하는 데서 끝나지 않고 서버의 `/auth/login`을 호출하여 자격 증명을 즉시 검증한다.

```text
govfs login
  Server URL: http://localhost:3000
  Username: user
  Password: ********
```

로그인에 성공하면 서버 URL, 사용자 이름, access token 및 만료 시간만 기존 로컬 설정 파일에 저장한다. 비밀번호는 로그인 요청에만 사용하고 파일에 저장하지 않는다. 로그인 실패 시 기존 세션 파일을 덮어쓰지 않는다.

다른 CLI 명령의 동작은 다음과 같이 단순화한다.

- 유효한 token이 있으면 그대로 사용한다.
- token이 없거나 만료되었으면 대화형 로그인을 자동 실행하지 않고 `govfs login` 실행을 안내한다.
- `govfs mcp`도 같은 세션을 사용하며 만료 시 즉시 오류를 반환한다.
- 기존 `--config`, `-c` 플래그는 로컬 설정 경로를 지정하는 용도이므로 유지한다.
- `govfs config` alias와 평문 비밀번호 기반 자동 로그인은 유지하지 않는다.

초기 구현에서는 refresh token을 추가하지 않는다. access token 만료 후 사용자가 다시 `govfs login`을 실행한다.

## 기존 데이터 이전

기존 단일 사용자 BadgerDB는 최초 관리자 드라이브로 이전한다.

1. 서버를 중지하고 기존 DB 백업을 만든다.
2. 최초 관리자 계정을 생성해 UUID를 확정한다.
3. 기존 DB 디렉터리를 `drives/{admin-uuid}`로 이동한다.
4. 서버를 시작하고 목록, 파일 읽기 및 쓰기를 확인한다.

Badger 내부 키와 값은 수정하지 않는다. 자동 마이그레이션은 잘못된 경로 이동 시 복구가 어려우므로 초기 구현에 포함하지 않고 별도 CLI 또는 운영 절차로 수행한다.

## 보안 조건

- 사용자 ID는 검증된 JWT와 사용자 DB에서만 얻는다.
- 사용자 이름이나 요청 파라미터로 드라이브 경로를 만들지 않는다.
- 관리자 라우트와 파일 라우트의 권한 검사를 분리한다.
- 오류 메시지에 사용자 존재 여부, 비밀번호 해시, DB 경로 또는 암호화 키를 포함하지 않는다.
- 로그인 실패 메시지는 사용자 없음과 비밀번호 불일치를 구분하지 않는다.
- 사용자 DB와 드라이브 루트는 서비스 계정 외의 OS 사용자가 읽을 수 없게 배치한다.
- 이 구조는 애플리케이션 수준 격리이며 동일 프로세스 침해나 서버 운영자의 접근을 방지하지 않는다.

## 구현 순서

1. 사용자 모델, 저장소와 최초 관리자 부트스트랩을 추가한다.
2. 로그인과 JWT 미들웨어를 사용자 UUID 기반으로 변경한다.
3. CLI의 `config` 명령과 비밀번호 저장을 `login`과 token 저장으로 교체한다.
4. `DriveManager`와 종료 처리를 추가한다.
5. VFS 요청이 현재 사용자의 드라이브를 선택하도록 변경한다.
6. SSE 이벤트와 클라이언트 조회를 사용자별로 제한한다.
7. 사용자 관리 및 상태 API를 추가한다.
8. Web UI의 로그인 응답과 관리자 화면을 연결한다.
9. 기존 데이터 이전 절차를 검증한다.

## 검증

최소한 다음 동작을 자동 테스트한다.

- 같은 사용자 이름의 중복 생성을 거부한다.
- 일반 사용자가 관리 API를 호출하면 `403 Forbidden`을 반환한다.
- 비활성화된 사용자의 기존 JWT 요청을 거부한다.
- 최초 관리자 설정은 빈 사용자 DB에서만 계정을 생성한다.
- `govfs login` 실패 시 기존 세션을 보존하고 비밀번호를 저장하지 않는다.
- token이 없거나 만료된 CLI 명령은 `govfs login` 실행을 안내한다.
- 두 사용자가 같은 VFS 경로와 파일 UUID를 사용해도 서로 조회하거나 변경하지 못한다.
- 관리자가 다른 사용자의 파일 ID로 조회해도 자신의 드라이브만 검색한다.
- 동일 사용자에 대한 동시 요청이 하나의 Badger 객체를 재사용한다.
- 한 사용자의 SSE 이벤트와 클라이언트 목록이 다른 사용자에게 노출되지 않는다.
- 서버 종료 시 시스템 DB와 열린 사용자 DB가 모두 닫힌다.
- 기존 관리자 드라이브의 백업, 복원 및 암호화 키 회전이 유지된다.

## 완료 기준

- 관리자와 일반 사용자가 로그인할 수 있다.
- 서버 설정에서 인증 비활성화와 기존 단일 계정 필드가 제거된다.
- CLI가 `govfs login`으로 인증하며 로컬 파일에 비밀번호를 저장하지 않는다.
- 각 사용자의 모든 VFS 작업이 독립된 BadgerDB에서 수행된다.
- 관리자에게 다른 사용자의 파일 접근 경로가 제공되지 않는다.
- 사용자 비활성화와 역할 변경이 기존 토큰에도 적용된다.
- SSE와 관리 상태 응답에서 사용자 파일 정보가 교차 노출되지 않는다.
- 기존 Badger VFS 저장 형식과 클라이언트의 VFS API 경로가 유지된다.
- `go build ./...`와 관련 단위 및 통합 테스트가 통과한다.
